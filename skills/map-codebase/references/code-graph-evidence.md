# Code Graph Evidence

Functionary may provide a compact `functionary-code-graph-evidence` JSON bundle generated by an optional static analyzer. Use it to accelerate repository inspection, not to replace architectural judgment.

## Reading the bundle

- `index` reports analyzer coverage and graph size. Counts are diagnostic; they are not city node counts.
- `architecture` summarizes languages, packages, entry points, routes, resources, layers, clusters, and hotspots when the analyzer can infer them.
- `graphSchema` lists the kinds of entities and relationships the analyzer actually found.
- `relationships` is a capped sample of calls, imports, configuration, handlers, writes, and related static links. It is intentionally incomplete.
- `limitations` records constraints that must remain visible in your reasoning.

## Trust rules

1. Treat the bundle as derived static evidence. It can support `declared` or `inferred` claims after source verification, but never `observed` runtime claims.
2. Verify candidate boundaries in manifests, entry points, infrastructure definitions, configuration, or representative implementation files.
3. Prefer repository-relative source paths from verified files. Do not cite the evidence bundle itself in the final city map.
4. Ignore graph noise such as utility functions, generated code, test helpers, and unresolved dynamic calls unless they materially explain the system.
5. Use graph relationships to discover meaningful flow, then express that flow at the architectural level. Do not create one room per package, file, class, or function.
6. If analyzer evidence conflicts with source or repository documentation, trust the primary repository evidence and add a warning only when the ambiguity matters.
